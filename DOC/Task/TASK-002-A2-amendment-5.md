# TASK-002-A2: поправка 5 (ошибка метрики: `Rigidbody2D.GetPoint` считает наоборот)

> **Модель для оператора: Grok.** Приоритет над поправками 1–4 и над ADR-003-a3 A15 п. 4 / ADR-003-a2 A10 в части функции пересчёта точки. Рапорт D1 и скриншоты разобраны.

## Диагноз (ошибка архитектора)
В поправках 2 (B2) и 3 (C0) я написал «читать позу тела через `Rigidbody2D.GetPoint(localAnchor)`». Это неверно. В Unity:
- `Rigidbody2D.GetPoint(worldPoint)` — **мир → локаль** (аналог `InverseTransformPoint`);
- `Rigidbody2D.GetRelativePoint(localPoint)` — **локаль → мир** (аналог `TransformPoint`, по позе тела, без интерполяции).

Доказательство по `c0_joint_dump.txt`: у сегмента 1 (`pos = (0.42, 0)`, `rot = 0`, `anchor = (−0.21, 0)`) дамп печатает `worldAnchorA = (−0.64, 0)`. Верное значение `(0.21, 0)`. Печатается `anchor − pos`. Для сегмента 0 (`pos = 0`) то же значение сходится, поэтому `worldAnchorB` у шарнира 0 «верный». Расчёт для сцены при −25°: `R⁻¹((−0.42, 0) − L·dir) = (−0.804, −0.178)`, дамп сцены даёт `(−0.808, −0.179)`. Совпадение до третьего знака.

Следствие:
- физика цепи, скорее всего, исправна: `autoConfigureConnectedAnchor = false`, якоря и расстановка верны;
- невязка 0.827, 10.7 при 1 с и `R_rest` 5.33 — артефакт метрики, а не геометрии;
- меш считает по `transform.TransformPoint` и совпадает с капсулами (смещение 0.041), в Play лента выглядит цельной — это согласуется с диагнозом;
- **все числа зазора и R**, снятые функцией `GetPoint` (C0, D1, любые прогоны SpikeBench после B2), недействительны. Это же касается выводов D1 о «сборке цепи».
